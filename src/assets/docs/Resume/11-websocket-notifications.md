# Real-Time WebSocket Notifications: Presence-Aware Delivery

## Resume Line
> "Improved user engagement by 40% by enhancing the real-time WebSocket notification system to only alert active viewers when product instructions were updated."

## TL;DR
This bullet tests whether you understand WebSockets as a genuine stateful, bidirectional protocol (not just "a fancier AJAX call") and whether you can reason about *presence* — knowing who's actually looking at a resource right now, across multiple browser tabs/devices, in a way that survives disconnects and scales past a single server instance. The core story: notifications were originally broadcast to everyone subscribed to a product (or worse, polled), which produced noisy, easily-ignored alerts; you added active-viewer tracking (subscription-scoped presence, likely with a heartbeat/last-seen mechanism) so only people currently looking at that product's instructions got pinged, making the notification meaningfully relevant — hence the engagement lift.

## The Story (STAR-style anchor)
**Situation:** At Enosis Solutions, our Angular + Spring Boot platform had a product-instructions module where multiple field technicians could view a given product's setup/repair instructions at the same time. When an author updated instructions, the original implementation broadcast a notification to *every* user who had ever opened that product's page, via a STOMP topic keyed by product ID. Analytics showed most of these notifications were dismissed unread or triggered when the user wasn't even in the app — dashboard engagement metrics for the "instructions updated" notification type showed a very low click-through, and support flagged it as "just noise" in a couple of user interviews.

**Task:** Make the notification meaningfully targeted — alert people who are actually looking at (or have very recently looked at) that product's instructions right now, not everyone who's ever viewed it, so a notification reliably means "something relevant to what you're doing changed."

**Action:** I redesigned the subscription model so that opening a product's instructions page sent a `PRESENCE_JOIN` STOMP message over the existing WebSocket connection, registering the session in a Redis-backed presence set keyed by `product:{id}:activeViewers`, with a TTL refreshed by a lightweight heartbeat every 20 seconds from the Angular client (using RxJS `interval` while the component was in view, paused on `visibilitychange` when the tab was backgrounded). Leaving the page (route change, tab close via `beforeunload`, or heartbeat expiry) removed the entry. On an instructions update, the backend published to a STOMP topic scoped as `/topic/product/{id}/updates`, but instead of every historical subscriber receiving it, I fanned it out only to session IDs currently present in that product's active-viewer set, using Spring's `SimpMessagingTemplate.convertAndSendToUser` for a targeted per-session send rather than a broadcast topic. Because we ran multiple Spring Boot instances behind a load balancer, I backed the STOMP broker relay with Redis pub/sub (rather than the default in-memory simple broker) so a presence update or notification published from one instance correctly reached WebSocket sessions connected to a different instance.

**Result:** The "instructions updated" notification's click-through/acknowledgment rate rose significantly post-change (from a product-analytics dashboard I didn't own but pulled figures from for the team retro) — the ~40% figure came from comparing 30-day click-through rate before vs. after rollout for that notification type specifically, holding notification volume-per-update roughly constant. Anecdotally, support also reported fewer "why am I getting notified about things I don't work on" complaints.

## Q&A — Foundational

**Q: What is a WebSocket, and how is it fundamentally different from an HTTP request?**
A: WebSocket is a protocol that upgrades an initial HTTP handshake (`Upgrade: websocket` header) into a persistent, full-duplex TCP connection — after the handshake, either side can push frames at any time without a new request/response cycle. HTTP is inherently request-then-response; the server can't initiate a send. WebSocket keeps one long-lived connection open, which is what makes true server push possible without polling overhead.

**Q: What is STOMP, and why is it layered on top of raw WebSockets in a Spring app?**
A: STOMP (Simple/Streaming Text Oriented Messaging Protocol) is a lightweight messaging protocol that gives WebSocket frames structure — destinations (`/topic/...`, `/queue/...`), a subscribe/publish model, and headers — similar in spirit to how HTTP gives TCP structure. Raw WebSockets are just a byte/text stream with no built-in concept of "subscribe to this topic" or "send to this specific user"; Spring's `spring-messaging`/`spring-websocket` support uses STOMP so you get pub/sub semantics, `@MessageMapping` controller methods, and per-user destinations out of the box instead of hand-rolling a message-routing protocol.

```java
@Configuration
@EnableWebSocketMessageBroker
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {
    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws").setAllowedOrigins("https://app.enosis.example").withSockJS();
    }
    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableStompBrokerRelay("/topic", "/queue")
                .setRelayHost("redis-broker").setRelayPort(61613);
        registry.setApplicationDestinationPrefixes("/app");
    }
}
```

**Q: What does "presence" mean in this context, and how did you track it?**
A: Presence is knowing, at any moment, which sessions/users are actively engaged with a given resource — here, which users currently have a specific product's instructions page open. I tracked it as a Redis Set (`SADD product:{id}:activeViewers {sessionId}`) with a per-entry TTL refreshed by a client heartbeat; membership in that set at notification-send time defined "active viewer," as opposed to relying on a static subscription list that never expired.

**Q: Walk through what happens, end to end, when the Angular client opens the instructions page.**
A: (1) On app load, the Angular client establishes a single STOMP connection over SockJS (`@stomp/stompjs`) to `/ws`. (2) On navigating to the instructions page for product 42, the component sends `stompClient.publish({destination: '/app/product/42/join'})`, and subscribes to `/topic/product/42/updates`. (3) The server's `@MessageMapping("/product/{id}/join")` handler adds the session to the Redis presence set and starts expecting a heartbeat. (4) A `setInterval`-driven heartbeat (paused when `document.hidden`) republishes a `keepalive` message every 20s, refreshing the Redis TTL. (5) On navigating away or closing the tab, an explicit `leave` message (sent from `ngOnDestroy`/`beforeunload`) removes the session immediately; if that message is lost (hard crash/network drop), the TTL expiry cleans it up within 20-40 seconds anyway.

**Q: How do you send a message to one specific user versus broadcasting to a topic in Spring's STOMP support?**
A: `SimpMessagingTemplate.convertAndSend("/topic/product/42/updates", payload)` broadcasts to every subscriber of that topic. `convertAndSendToUser(username, "/queue/updates", payload)` routes to a specific authenticated user's private queue (Spring internally rewrites the destination to include a session-specific suffix). For our fan-out-to-active-viewers case, I looked up the current presence set for the product, then iterated it calling `convertAndSendToUser` per active session rather than relying on the broadcast topic, since the whole point was to *not* reach everyone subscribed.

**Q: What's a heartbeat/keepalive for, concretely, in a WebSocket system?**
A: Two purposes: (1) detecting dead connections — TCP doesn't always notify you promptly when a peer vanishes (closed laptop lid, network drop without a clean FIN), so an app-level ping/pong or heartbeat message lets you time out a session that's silently gone; STOMP itself supports heartbeats natively (`stompClient.configure({heartbeatIncoming, heartbeatOutgoing})`). (2) In our case specifically, the heartbeat doubled as the presence-TTL refresh mechanism, so "actively viewing" degraded gracefully to "not viewing" within a bounded, short window after a user actually left, without requiring a perfectly reliable "leave" signal.

**Q: How did the Angular side avoid flooding the server with unnecessary heartbeats?**
A: Two guards: `document.visibilitychange` paused the heartbeat interval when the tab was backgrounded (so a backgrounded tab's viewer entry naturally expired via TTL, correctly reflecting they weren't "actively viewing"), and the heartbeat was scoped per open product page, not global — a user with the instructions page open in three tabs sent three lightweight heartbeats, but that's a deliberate accuracy trade-off (they genuinely have three active views), not waste.

## Q&A — Why This, Not That (Decision Tree)

**Q: Why WebSockets instead of just polling the "last updated" timestamp every N seconds?**
A: Polling means every client hits the server on a fixed interval regardless of whether anything changed, so cost scales with (clients × poll frequency) rather than with actual update events — for thousands of concurrently open product pages, that's a lot of wasted round trips for a "nothing changed" response. It also caps freshness at the poll interval; if you want near-instant notification, you need short intervals, which multiplies the waste. WebSockets push exactly when there's something to push, and the always-open connection is also what let us build genuine bidirectional presence signaling (`join`/`leave`/heartbeat), which polling has no natural equivalent for.

*But what about Server-Sent Events (SSE) — server push without needing bidirectional communication, and simpler than WebSocket?* — SSE was genuinely a candidate for the notification-push half of this. It's simpler (plain HTTP, auto-reconnect built into `EventSource`), and we only needed server-to-client push for the actual update notification. But SSE is one-directional — the client can't send the `join`/`leave`/heartbeat presence signals over the same connection, so I'd have needed a second channel (regular HTTP POSTs for presence) anyway, which adds its own complexity (correlating two separate connections per session, handling their failure independently). Since we already had a bidirectional STOMP/WebSocket connection in the app for other real-time features (live chat-style comments on instructions), reusing it for presence + notifications was less net-new infrastructure than SSE-plus-HTTP-polling-for-presence would have been.

*OK, but doesn't a single shared WebSocket connection for everything create a single point of failure for multiple unrelated features?* — Somewhat — if the WebSocket connection drops, both presence and live-notification delivery degrade together. I mitigated this by making presence loss non-catastrophic: the TTL-based Redis expiry means a dropped connection self-heals within one heartbeat window (worst case, the user is briefly treated as "not viewing," which just means they don't get an instant notification — not a correctness failure, just a missed real-time nudge that they'd still see as an unread badge on next load) and STOMP.js's built-in reconnect-with-backoff automatically re-subscribes and re-joins presence on reconnect.

**Q: Why only alert active viewers instead of broadcasting the update to everyone who's ever subscribed — isn't more notification coverage generally safer?**
A: The original broadcast-to-everyone behavior is exactly what was producing the low engagement — it optimized for reach over relevance, training users to ignore the notification type entirely because most instances didn't apply to what they were doing right then. Alerting only active viewers trades reach for relevance: fewer notifications sent, but each one is far more likely to be actionable ("the page you're looking at right now just changed"), which is what actually moved the engagement metric.

*But what if a user updates instructions and nobody is actively viewing — doesn't the update just go unnoticed?* — Right, and that's a real gap we had to explicitly design for — active-viewer alerting is an *addition* to, not a replacement for, a durable notification. Users not currently viewing still got a standard persisted in-app notification (stored in Postgres, shown as an unread badge/notification-center entry on next login) — the WebSocket active-viewer push was specifically the "someone is looking at this right now, interrupt them live" channel, layered on top of the always-reliable async channel.

*OK, but doesn't maintaining two notification paths (live push + persisted async) risk them drifting or double-notifying the same user?* — Yes, so I made the persisted notification the single source of truth (written first, always, on update) and the WebSocket push a purely additive "and also nudge them live if they're currently here" step reading from the same write — if a user was both actively viewing and would've gotten the async notification, the live push suppressed the badge-increment side effect for that specific user/notification pair (tracked via the same notification ID) so they didn't see the same thing counted twice.

**Q: How exactly did you determine "active" — was it just "has the page open," and is that too coarse?**
A: Initially yes, "has the page open and connected" (tab open, heartbeat current) was the bar, which is coarse — someone could have the tab open but be scrolled away, in a different application, or the tab backgrounded. I refined "active" to also require `document.visibilitychange`'s foreground state, i.e., heartbeats paused when backgrounded, so presence more closely tracked "the tab is currently the one they're looking at," not just "technically open in some background tab." I didn't go further (e.g., mouse-movement/scroll tracking for true attention-tracking) — that felt like it was solving a problem we didn't actually have evidence for, and it adds real client-side complexity and potential privacy/perception concerns (tracking exactly how a user is interacting with a page) for a use case where "foregrounded tab" was already a big accuracy improvement over "ever subscribed."

**Q: What happens on reconnect after a dropped connection — does presence get duplicated, lost, or stale?**
A: On reconnect, STOMP.js's client re-establishes the connection and my code explicitly re-sends the `join` message for whatever product page is currently mounted (driven by Angular component lifecycle, not assumed carried-over server state) — the server treats every `join` as idempotent (`SADD` is naturally idempotent; re-adding an existing member is a no-op) so there's no duplication risk. Staleness is bounded by the TTL: if the old session's Redis entry hadn't yet expired when a new session for the same user reconnects, both entries could briefly coexist (worst case, if the user opened two tabs), but since each is keyed by session ID, not user ID, that's actually correct behavior (they do have two active views), not a bug.

**Q: How does this scale to many concurrent connections across multiple server instances — where do sticky sessions and a pub/sub backplane come in?**
A: Two separate scaling concerns. First, WebSocket connections are stateful TCP connections held open on a specific server instance — a load balancer needs either sticky sessions (route a given client's HTTP-upgrade-then-WebSocket traffic consistently to the same backend instance) or the app needs to not care which instance holds the connection. We used sticky sessions (cookie-based affinity at the load balancer) so a client's WebSocket lifecycle stayed simple and pinned to one instance. Second, even with sticky sessions, a notification triggered by an API call landing on instance A needs to reach a WebSocket connection that might be held open on instance B — that's what the Redis-backed STOMP broker relay (`enableStompBrokerRelay`, or in simpler setups, a Redis pub/sub-backed `SimpMessagingTemplate`) solves: publishing to `/topic/product/42/updates` on instance A gets relayed via Redis to every instance, and whichever instance actually holds the relevant session's connection delivers it.

*But what happens to the presence set itself under multi-instance deployment — is the Redis Set shared or per-instance?* — Shared — the presence set (`product:{id}:activeViewers`) lives in Redis, not in any single instance's memory, specifically so that any instance handling the "send notification" logic can query the full, cross-instance-accurate set of active viewers, regardless of which instance each of those viewers' WebSocket connections happen to be pinned to.

## Q&A — Trade-offs & Failure Modes

**Q: What actually breaks in production with this design?**
A: A few concrete issues we hit: (1) Redis becoming a soft single point of failure for presence — a Redis blip meant presence lookups failed or returned stale/empty sets, which we handled by failing open on the notification side (if presence lookup errors, fall back to the safe default of "no live push, rely on the async notification" rather than crashing the update-save transaction) rather than failing closed. (2) Load-balancer sticky-session misconfiguration during a rolling deploy caused a batch of clients to get silently reconnected to a different instance mid-session, briefly duplicating/losing presence entries until the next heartbeat cycle self-corrected — not catastrophic, but visible as a short blip in "who's active" during deploys. (3) Clock skew between the heartbeat interval and Redis TTL configuration (TTL slightly shorter than 2x heartbeat interval) caused viewers to be occasionally marked "inactive" between heartbeats under network jitter, producing a few missed live notifications — fixed by setting TTL to 2.5x the heartbeat interval, giving one full missed-heartbeat's worth of slack.

**Q: What's the cost/complexity trade-off of presence tracking versus simple topic broadcast?**
A: Broadcast-to-topic is close to zero extra infrastructure — the broker handles fan-out natively. Presence tracking adds a stateful layer (Redis sets, TTL management, heartbeat protocol, join/leave lifecycle on both client and server) that has to be built, tested for edge cases (reconnects, multi-tab, backgrounding), and monitored. That complexity is only worth it when "who's currently looking at this" is genuinely a better targeting signal than "who has ever cared about this" — for a low-traffic feature or one where all subscribers plausibly want every update, plain broadcast is simpler and I wouldn't add presence tracking.

**Q: When would you NOT build active-viewer-scoped notifications?**
A: If the update event itself is rare and high-stakes enough that everyone subscribed genuinely should know regardless of whether they're looking right now (e.g., "this product has been recalled" versus "someone tweaked a formatting detail in the instructions"), scoping to active viewers would actively suppress notifications that matter to people who happen not to be looking at the page in that moment — for that class of event we kept the old broadcast-to-all-subscribers-async behavior deliberately, and only applied active-viewer-scoped *live* pushes to the lower-stakes, high-frequency "content updated" event where relevance mattered more than guaranteed reach.

**Q: What's a failure mode around privacy/trust with presence tracking that you had to think about?**
A: Presence data (who's looking at what, right now) is itself sensitive if exposed beyond its intended use — we deliberately never surfaced "who else is currently viewing this page" to end users (no "3 people are viewing this" UI), because that wasn't the feature we were building and it introduces a presence-visibility decision (do coworkers want to be seen as viewing something?) we hadn't gotten product/legal sign-off on. Keeping presence data purely internal to the notification-targeting decision, never exposed via any API response to other users, avoided that whole can of worms.

**Q: What's the failure mode if the `leave` message never fires and TTL is misconfigured too long?**
A: A user who closed their laptop lid (no `beforeunload` fired, network just vanished) stays marked "active" until TTL expiry — if TTL were set too generously (say, 10 minutes) that's a 10-minute window where a genuinely-gone user still receives a live push notification they'll never see, and worse, is being counted in "active viewer" metrics that might feed other logic. We kept TTL tight (heartbeat-interval-driven, tens of seconds not minutes) specifically to bound this staleness window tightly, accepting the cost of slightly more frequent heartbeat traffic in exchange for presence data that's rarely more than 20-50 seconds stale.

## Q&A — Scaling & Extending

**Q: How would this evolve at 10x the concurrent users?**
A: The Redis presence sets and pub/sub relay approach scales fairly linearly and was already designed for multi-instance, so the more pressing changes would be: connection-count capacity planning per instance (each WebSocket connection holds server-side memory/file-descriptor resources, so horizontal scaling of the WebSocket-handling tier, not just the API tier, becomes its own capacity question), and potentially moving from a general-purpose Redis instance to a dedicated Redis Cluster or a purpose-built pub/sub system (NATS, or a managed service) if presence-set churn (heartbeats × users) started to dominate that Redis instance's load alongside other caching uses.

**Q: What would you add next if you kept building this out?**
A: Batched/debounced live notifications — if an author saves multiple quick edits to the same product within a short window, currently each save could trigger a separate live push; I'd add a short debounce (e.g., 5-10 seconds) on the publish side so rapid successive edits collapse into one notification. I'd also add a lightweight "typing/editing in progress" presence signal so an active viewer sees "this page is currently being edited" proactively, rather than only finding out after the fact via a push notification.

**Q: How would you extend presence tracking to also support cross-device consistency (same user active on both a laptop and a mobile app)?**
A: Since presence is already keyed by session ID rather than user ID, multiple devices/sessions for the same user naturally coexist as separate presence-set entries — the notification fan-out logic would need to dedupe at delivery time per user (if a user has two active sessions on the same product, they should get one meaningful in-app experience per device, not necessarily suppressed, but any cross-device "mark as seen" state would need a shared per-user read-state store, likely the same Postgres notification table already used for the async/persisted path, rather than inventing new state.

**Q: If you needed to prove causality (not just correlation) for the 40% engagement number more rigorously, what would you do differently?**
A: Run it as an actual A/B test — route a random subset of users through the old broadcast-to-all-subscribers path and the rest through the new active-viewer-scoped path for a fixed window, then compare click-through/engagement between cohorts rather than a before/after time-series comparison (which is vulnerable to seasonality, concurrent unrelated changes, or a Hawthorne effect from users noticing *any* change to notification behavior). In our case we did a straightforward before/after comparison of the specific notification type's 30-day click-through rate, which is a real, checkable number but weaker evidence of causation than a proper randomized rollout would have been — I'd say that plainly if pushed on it in an interview.

# Database Performance Tuning: Index & Query Restructuring

## Resume Line
> "Conducted performance audits and restructured indexes and queries; decreased DB I/O by 35% and reduced report load times by 45%."

## TL;DR
This bullet is testing whether you actually understand *how* a query planner decides to hit disk vs. use an index, or whether "I added some indexes" is the full depth of your knowledge. The interviewer wants to see the diagnostic process (how you found the slow queries), the specific fix (composite index design, covering indexes, query rewrites, avoiding N+1), and — critically — how you proved the 35%/45% numbers with real before/after measurement rather than a vibe. The core story: a reporting module doing full table scans and N+1 lookups against a growing Postgres/Oracle table, diagnosed with `EXPLAIN ANALYZE` and slow query logs, fixed with composite/covering indexes and query rewrites, validated with production-representative load tests and DB metrics (buffer cache hit ratio, physical reads).

## The Story (STAR-style anchor)
**Situation:** At Enosis, one of our client's core admin dashboards had a "Monthly Activity Report" screen that took 8-12 seconds to load once the `orders` table crossed ~6 million rows and `order_items` crossed ~22 million. Support tickets started coming in about timeouts during month-end when finance ran the report repeatedly.

**Task:** I was asked to profile the reporting path and bring load time down without redesigning the whole reporting architecture (no time budget for a data warehouse/ETL project).

**Action:** I turned on `pg_stat_statements` (Postgres) to rank queries by total execution time and total I/O (`shared_blks_read`), then ran `EXPLAIN (ANALYZE, BUFFERS)` on the top 5 offenders. Found two root causes: (1) the report's date-range filter on `orders.created_at` combined with a `status` filter was doing a sequential scan because the only index was on `created_at` alone, and the planner estimated low selectivity; (2) the report was doing an N+1 pattern from the Spring Data JPA repository — fetching orders, then lazily fetching `order_items` per order in a loop, generating ~2,000 round-trip queries for a single report run. I fixed the first with a composite index `(status, created_at)` ordered to match filter selectivity, and a covering index that included the aggregated columns to enable an index-only scan. I fixed the second by rewriting the JPA query to use a `JOIN FETCH` with pagination, and batched the aggregation into a single SQL query with `GROUP BY` instead of doing it in Java. I validated using a staging environment restored from a production snapshot, ran the report 20 times before and after using `EXPLAIN ANALYZE` timing plus wall-clock via JMeter, and pulled `pg_stat_user_tables`/`pg_statio_user_tables` diffs to measure physical block reads before and after.

**Result:** Physical disk I/O (blocks read from disk vs. cache) for the report's query set dropped by ~35%, and end-to-end report load time dropped from ~9.5s average to ~5.2s (about 45%). I also documented the index additions and the reasoning in a short runbook so the next engineer wouldn't blindly add redundant indexes later.

## Q&A — Foundational

**Q: What type of database optimization techniques have you used? (Don't just say "indexing.")**
A: It depends on where the bottleneck actually is, and I diagnose with `EXPLAIN ANALYZE` / `pg_stat_statements` before picking a tool rather than reaching for indexing by reflex. Broadly, across my work:
- **Access-path level:** composite and covering indexes when the planner has no efficient path to selective rows (this bullet's story) — column order matters, equality-filtered columns before range-filtered ones.
- **Query-shape level:** rewriting the query itself — fixing N+1 patterns with `JOIN FETCH` or batch fetching, moving aggregation into SQL (`GROUP BY`) instead of looping in application code. No index fixes a query-count problem; only a rewrite does.
- **Schema/setup level:** automating schema, trigger, and index generation from Hibernate mappings (a separate resume bullet) so the baseline schema is correct before you ever need to tune it reactively.
- **Caching level:** Redis caching (another resume bullet) to avoid hitting the DB at all for high-frequency reads — this is a different lever than making the DB itself faster.
- **Bulk-operation level:** batched JDBC writes and multithreaded parallel processing for large record sets (3M+ records bullet) instead of row-by-row sequential I/O.
- **Pagination level:** replacing `LIMIT/OFFSET` pagination with keyset (cursor-based) pagination on large, frequently-paged result sets — `OFFSET` forces the DB to scan and discard every row before the offset, so page 500 at offset 50,000 is far more expensive than page 1, and gets linearly worse the deeper you page. Keyset pagination (`WHERE (created_at, id) < (:lastSeenCreatedAt, :lastSeenId) ORDER BY created_at DESC, id DESC LIMIT 20`) seeks directly via an index instead of scanning-and-discarding, so page 500 costs the same as page 1.
- **Structural level, for future growth:** denormalization/materialized views to avoid paying join-and-aggregate cost at read time, and partitioning or read-replica offload once table size or reporting load outgrows what indexing alone can fix.
The one-word "indexing" answer is fine as a first sentence, but I always follow it with "depending on the bottleneck" and name at least two others — it signals I have a diagnostic process, not just one tool I reach for automatically.

**Q: Why does `OFFSET` pagination get slower the deeper you page, and how does keyset pagination avoid that?**
A: `LIMIT 20 OFFSET 50000` doesn't jump to row 50,000 — the executor still has to walk 50,020 rows in sort order (via index or scan) and throw away the first 50,000 before returning the last 20, so cost grows linearly with the offset even though the index makes each individual row cheap to find. Keyset pagination avoids this by remembering the last row's sort-key values from the previous page and using them as a `WHERE` predicate (`WHERE (created_at, id) < (:lastCreatedAt, :lastId)`) instead of a row count — that's a direct index seek to the right starting point every time, so page 2 and page 5,000 cost the same. The trade-off: keyset pagination can't jump straight to an arbitrary page number ("go to page 47") since there's no offset concept, only "next page from here" — fine for infinite-scroll feeds and APIs, not ideal for a UI with numbered page links, where I'd either accept the `OFFSET` cost at a capped max depth or pair keyset pagination with a separate approximate total-count query.

**Q: Walk me through what happens when Postgres executes a query with no useful index — what does "full table scan" actually cost?**
A: The planner reads every page (block, typically 8KB) of the table's heap into the buffer cache/disk sequentially, applies the filter predicate row-by-row, and discards non-matching rows after reading them. For a table with millions of rows spanning many gigabytes, this means potentially reading the entire table into memory even if the result set is a tiny fraction of it — cost is O(table size), not O(result size). If the table doesn't fit in `shared_buffers`, you get real disk I/O, which is orders of magnitude slower than sequential reads from OS cache and even more so than an index lookup.

**Q: What is a B-tree index actually doing under the hood, and why does it turn an O(n) scan into something faster?**
A: A B-tree index is a balanced, sorted tree structure where each node holds a range of key values and pointers to child nodes or, at the leaf level, pointers (TIDs — tuple IDs / ctid in Postgres) back to the actual heap rows. Looking up a value means walking from root to leaf in O(log n) comparisons, then following the row pointer(s) to fetch the actual row from the heap (unless it's an index-only scan). For a table of 20M rows, that's roughly 24 comparisons instead of scanning 20M rows.
```sql
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
```

**Q: Explain composite index column order — why does `(status, created_at)` behave differently from `(created_at, status)`?**
A: A composite B-tree index is sorted first by the leftmost column, then by the next column within each group of equal leftmost values. The index is only efficiently seekable ("can use the index to jump directly to a range") for a leading prefix of columns used with equality or range predicates. If your query is `WHERE status = 'COMPLETED' AND created_at BETWEEN X AND Y`, putting `status` first lets Postgres seek directly to the `COMPLETED` block of the tree and then range-scan within it (a small, sorted subset). Reverse the order — `(created_at, status)` — and a range predicate on `created_at` first means the `status` equality can only be applied as a filter *after* finding the created_at range, which is significantly less selective if status has few distinct values spread across all dates. General rule: equality columns before range columns, and put the most selective / most consistently-filtered column first.

**Q: What's a covering index and why did you use one?**
A: A covering index includes all the columns a query needs — filter columns, join columns, *and* the columns it needs to return (either in the key or via `INCLUDE`) — so the query can be satisfied entirely from the index without touching the heap. In Postgres this enables an "index-only scan," visible in `EXPLAIN` output. It matters because heap access from a B-tree index normally requires a second random I/O per matching row (index leaf -> heap page); if the visibility map says the pages are all-visible, an index-only scan skips that entirely.
```sql
CREATE INDEX idx_orders_report_covering
  ON orders (status, created_at)
  INCLUDE (total_amount, customer_id);
```

**Q: How do you read an `EXPLAIN ANALYZE` output to tell if a query is actually slow because of I/O vs. CPU?**
A: I look at `EXPLAIN (ANALYZE, BUFFERS)` — the `Buffers: shared hit=X read=Y` line. `hit` means the block was already in the Postgres buffer cache (fast, memory); `read` means it had to be fetched from OS cache or disk (slower, and slower still if it's a genuine disk read rather than OS page cache). A high `read` count relative to `hit`, combined with a large gap between the planner's estimated rows and actual rows, points to either a cold cache or a stale statistics problem (need `ANALYZE` to refresh table stats) or a genuinely I/O-bound scan. I also check `Execution Time` vs. `Planning Time` — if planning time is disproportionately high, that's usually a sign of overly complex query structure or too many indexes to consider, not an I/O issue.

**Q: What's the N+1 query problem and how did it show up in your Hibernate/JPA code specifically?**
A: N+1 happens when you fetch a parent list (1 query) and then, due to lazy-loaded associations, trigger one additional query per parent to fetch its children — 1 + N queries total instead of 1 or 2. In our case, `List<Order> orders = orderRepository.findByCreatedAtBetween(start, end)` returned ~2,000 orders, and then the report code iterated over `order.getOrderItems()`, a `@OneToMany(fetch = LAZY)` association, triggering a separate `SELECT * FROM order_items WHERE order_id = ?` for each order — 2,000 extra round trips.
```java
@Query("SELECT o FROM Order o JOIN FETCH o.orderItems WHERE o.createdAt BETWEEN :start AND :end")
List<Order> findWithItemsInRange(@Param("start") LocalDateTime start, @Param("end") LocalDateTime end);
```

**Q: What's the difference between a slow query log and an APM tool for finding these problems, and which did you use?**
A: The Postgres slow query log (`log_min_duration_statement`) and `pg_stat_statements` extension capture query text, call count, total/mean execution time, and (with `track_io_timing` on) I/O timing — good for finding the worst offenders by *cumulative* impact, not just single slow runs. An APM tool (we had some New Relic dashboards, though not full APM tracing on this project) shows the request-level trace, so you can see a single HTTP request fanning out into 2,000 DB calls, which `pg_stat_statements` alone won't show you as directly since it aggregates by normalized query text. I used `pg_stat_statements` to find *which* queries were expensive in aggregate, and manual request tracing/logging (Hibernate's `show-sql` + statement count assertions in a local repro) to catch the N+1 pattern specifically.

## Q&A — Why This, Not That (Decision Tree)

**Q: Why add an index instead of just rewriting the query to be more efficient?**
A: They're not mutually exclusive, and I did both, but for different problems. The `status + created_at` filter was a data-access-path problem — no rewrite of that query would help without a supporting index because the planner has no efficient path to the matching rows regardless of how the SQL is phrased. The N+1 issue, by contrast, was a query *shape* problem (issuing the wrong number of queries), and no index fixes "you're doing 2,000 round trips" — that needed a `JOIN FETCH` rewrite. Rule of thumb: if `EXPLAIN` shows a full/sequential scan on a large table with a selective filter, think index; if the problem is a query *count*, think rewrite/batching.

**Q: Why not just denormalize the report data (e.g., a pre-aggregated summary table) instead of index tuning?**
A: I considered it, and it's actually the better long-term answer if reporting needs keep growing. But denormalization brings staleness and consistency complexity — you now need a job (Kafka consumer, scheduled ETL, or trigger-based) to keep the summary table in sync with `orders`/`order_items`, plus a story for how the report handles data that's a few minutes old, plus double-write bugs if the sync job fails silently. Given the team's time budget and that index tuning got us under the SLA (report needed to be under 6s, we hit ~5.2s), I chose the lower-risk, lower-operational-overhead fix first and flagged denormalization/materialized views as the next step if report volume or complexity grew.

**Q: But what if report requirements later need real-time joins across five tables with complex aggregations — doesn't index tuning eventually hit a wall?**
A: Yes — indexes help the planner find rows faster, but they don't reduce the fundamental cost of joining and aggregating large volumes at read time. At some point (and I'd watch for `EXPLAIN` showing large `HashAggregate` or `Sort` nodes spilling to disk, or planning/execution time creeping up again despite good index usage) the right move shifts to either a materialized view refreshed on a schedule (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) for near-real-time needs, or a proper OLAP/read-replica or warehouse (e.g., replicate into a columnar store) for heavy historical reporting, so you're not making OLTP tables pay OLAP-shaped query costs.

**Q: OK, but doesn't adding indexes hurt write performance? How did you decide it was worth it here?**
A: Every index adds overhead on INSERT/UPDATE/DELETE — the index B-tree has to be updated too, and more indexes means more random I/O and WAL volume per write. I checked the write pattern on `orders` first: it's an append-heavy table with relatively low update frequency (status changes a handful of times per order lifecycle, not per second), and the write volume was maybe a few hundred orders/minute at peak — nowhere near enough for the extra index maintenance to be a bottleneck. I also avoided just throwing indexes at every column; I picked exactly two indexes justified by the actual query patterns from `pg_stat_statements`, dropped one redundant single-column `status` index that became fully subsumed by the new composite index (a leading-column index is redundant once a composite index starts with that same column), so the net index count on the table barely changed.

**Q: What if the read query patterns are unpredictable — lots of ad-hoc filters from different report screens? Composite indexes only help exact matching patterns.**
A: True — a composite index on `(status, created_at)` doesn't help a query filtering only on `customer_id`. For genuinely ad-hoc, unpredictable filter combinations, I'd lean toward: (1) covering the top N query patterns from `pg_stat_statements` with targeted composite indexes rather than trying to index every combination, (2) for truly arbitrary filtering, consider a search-oriented store (Elasticsearch/OpenSearch) fed by CDC (Debezium/Kafka) if the ad-hoc querying becomes a first-class product feature, since B-tree composite indexes fundamentally don't scale to "any column, any combination." In our case, the report screens were a fixed, known set (maybe 6 report types), so targeted composite indexes were the right, low-complexity tool.

**Q: How exactly did you validate the 35% I/O and 45% load-time numbers — convince me it's not just "felt faster on my dev box"?**
A: Three things had to line up. First, environment: I used a staging DB restored from an anonymized production snapshot (same row counts, same data skew), not a synthetic dataset, because query planner behavior is extremely sensitive to actual data distribution and table statistics. Second, methodology: I ran the report 20 times before the change and 20 times after, on the same hardware, with the DB buffer cache pre-warmed identically each run (ran a warmup query first so I wasn't comparing a cold cache to a warm one), and took the median wall-clock time via a JMeter script hitting the actual report endpoint, not just the raw SQL in isolation — that captures serialization/network overhead too, which is what users actually feel. Third, the I/O number specifically came from `pg_stat_statements.shared_blks_read` and `pg_stat_database.blks_read` deltas over an identical fixed workload (same 20 report runs), not an estimate — I diffed the counters before and after the run window. 9.5s median -> 5.2s median load time is a 45.3% reduction; blocks read per run went from roughly 480,000 to about 310,000, a 35.4% reduction.

**Q: What if the improvement was actually mostly from better cache warmth in your test rather than the index change — how do you rule that out?**
A: That's exactly why I warmed the cache identically in both before/after runs and ran 20 iterations rather than one — a single lucky warm-cache run could absolutely mislead you. I also cross-checked with `EXPLAIN ANALYZE` plan shape directly: before, the plan showed `Seq Scan on orders (cost=... rows=...) Buffers: shared read=41230`; after, it showed `Index Only Scan using idx_orders_report_covering ... Buffers: shared hit=812`. That's a structural change in the access path, not just a cache-warmth artifact, which is the real proof — the plan itself changed from O(table) to O(matching rows via index).

## Q&A — Trade-offs & Failure Modes

**Q: What can go wrong with this approach in production that wouldn't show up in staging?**
A: Data skew is the big one — staging stats can drift from production if the snapshot ages, and the planner can flip from an index scan back to a sequential scan if table statistics go stale (autovacuum/auto-analyze lag) or if a parameter value used in a prepared statement causes a different plan to be chosen (parameter sniffing-adjacent behavior via generic vs. custom plans in Postgres after 5 executions). I mitigated this by making sure `autovacuum` was tuned aggressively enough on `orders` given its size, and monitoring `pg_stat_user_tables.n_dead_tup` and last autoanalyze time post-deploy.

**Q: When would you NOT add an index even if it would clearly speed up a slow query?**
A: If the table is extremely write-heavy (e.g., a high-frequency event/log table with thousands of inserts/sec) and the query being optimized is a rare, low-priority ad-hoc report, the write-amplification cost of maintaining another index on every insert may not be worth it — I'd rather solve that with a periodic export/rollup than tax every write path. Also, if the table is small (a few thousand rows), Postgres will often correctly choose a sequential scan anyway since it's cheaper than index overhead, and adding an index there is just extra maintenance cost for no benefit — I'd verify with `EXPLAIN` rather than assume "index = always better."

**Q: What's the failure mode with covering indexes specifically?**
A: They can quietly bloat — every column you `INCLUDE` gets duplicated into the index, so a wide covering index on a large table can end up comparable in size to (or larger than) a chunk of the table itself, costing extra disk space and slower writes (more bytes to write per insert/update). I kept the `INCLUDE` list narrow (just the two aggregate columns the report actually needed) rather than including everything "just in case."

**Q: What if the JOIN FETCH rewrite caused a Cartesian-product blow-up with pagination?**
A: That's a real Hibernate gotcha — `JOIN FETCH` on a `@OneToMany` combined with `Pageable`/`LIMIT` at the SQL level doesn't work correctly because the join multiplies rows before the limit is applied, so Hibernate has to do in-memory pagination and logs the infamous "firstResult/maxResults specified with collection fetch; applying in memory" warning, which can be worse than the N+1 it replaced for large result sets. I avoided this by fetching order IDs with pagination first (a lightweight query), then doing the `JOIN FETCH` for just that page of IDs using `WHERE o.id IN (:ids)` — two queries total instead of N+1, with correct pagination.

**Q: What's the cost/complexity trade-off of this work versus just throwing more hardware at it (bigger instance, more RAM)?**
A: Scaling hardware masks the symptom without fixing the algorithmic problem — a sequential scan on a table that's 2x bigger next year eats the hardware gain again, and vertical scaling has diminishing returns and real cost (bigger RDS/Aurora instance class is a recurring monthly cost, index tuning is a one-time engineering cost). I did check whether `shared_buffers`/`work_mem` tuning alone would help first (cheap to try), but it only marginally helped since the fundamental problem was scan strategy, not memory pressure — confirmed this by testing with `work_mem` bumped and seeing negligible change in the `EXPLAIN` plan choice.

## Q&A — Scaling & Extending

**Q: This worked at ~28M total rows across the two tables. What breaks at 10x that (280M rows)?**
A: The composite index itself stays roughly O(log n) for lookups, so it scales fine algorithmically, but a few things start to hurt: index size itself becomes large enough that a meaningful fraction may not fit in `shared_buffers`, reintroducing disk I/O for index pages themselves; `autovacuum` on a 280M-row table takes much longer and can fall behind, causing statistics staleness and bloat; and monthly report queries that scan even a "small percentage" of the table (say 2%) are now scanning 5.6M rows, which might justify partitioning `orders` by month/range (Postgres native declarative partitioning) so the report can prune to just the relevant partitions instead of relying purely on the index across the whole table.

**Q: If the team grew and multiple engineers were adding indexes ad-hoc, what would you put in place?**
A: I'd push for an index review step in PR review for any migration touching high-traffic tables, plus a dashboard (or scheduled query) surfacing unused indexes (`pg_stat_user_indexes.idx_scan = 0` over a rolling window) and redundant/overlapping indexes, so index sprawl gets caught before it silently taxes every write. I'd also want the `pg_stat_statements`-based "top N slow queries" review to be a recurring (e.g., monthly) practice, not a one-off audit triggered by a fire.

**Q: What would you add next if given another sprint on this?**
A: A materialized view for the heaviest report (refreshed nightly or via `CONCURRENTLY` on a schedule) since that report's aggregation was still doing real work even with the new indexes; and read-replica routing for reporting traffic specifically, so report queries don't compete for buffer cache and lock resources with the primary OLTP write path during month-end crunch.

**Q: How would this story change if the DB were Oracle instead of Postgres, given you've also worked with Oracle?**
A: Same fundamentals, different tools: I'd use `EXPLAIN PLAN` / `DBMS_XPLAN.DISPLAY_CURSOR` and AWR/ASH reports instead of `pg_stat_statements`, look at `Buffer Gets` and `Disk Reads` in the plan output instead of Postgres's `Buffers` line, and consider Oracle-specific options like a function-based index if the report filtered on a computed expression, or an Index-Organized Table if the table were primarily accessed by its primary key range. The diagnostic *process* — find the expensive query, read the plan, identify scan vs. seek, add the minimal index that changes the access path — is identical across engines.

## Rapid-Fire Follow-ups
- Q: What tool did you use to find the slow queries? A: `pg_stat_statements` combined with `EXPLAIN (ANALYZE, BUFFERS)`.
- Q: What's the difference between `EXPLAIN` and `EXPLAIN ANALYZE`? A: `EXPLAIN` shows the estimated plan only; `EXPLAIN ANALYZE` actually executes the query and shows real timing/row counts.
- Q: Leading column rule for composite indexes? A: Equality-filtered, high-selectivity columns first; range-filtered columns after.
- Q: What is an index-only scan? A: A scan that satisfies the query entirely from the index without touching the heap.
- Q: What Postgres feature tracks per-table dead tuples? A: `pg_stat_user_tables.n_dead_tup`, managed by autovacuum.
- Q: What caused the N+1 in your case? A: A `@OneToMany(fetch = LAZY)` association accessed in a loop over 2,000 parent rows.
- Q: Fix for N+1 in JPA? A: `JOIN FETCH` or a batch fetch size (`@BatchSize`), or fetching IDs first then a bounded `IN` query.
- Q: What's write amplification from indexing? A: Every additional index adds overhead to every INSERT/UPDATE/DELETE on that table.
- Q: How did you avoid a stale/cold-cache bias in benchmarking? A: Ran 20 iterations with identical warmup and took the median, before and after.
- Q: What's the next step beyond index tuning for this report? A: Materialized view or read-replica offload for reporting traffic.

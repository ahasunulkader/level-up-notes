🌐 Geohashing

Divides the world into a fixed grid. Each cell gets a short string. Longer string = smaller (more precise) area.

How Layers Work

Layer 1 splits the world into 4 cells: 0 1 2 3. Each cell then splits again into 4 more, giving Layer 2 cells like 20 21 22 23. The prefix encodes which region you're in.

Key Rule All Layer-2 cells inside cell 2 start with 2:
→ 20, 21, 22, 23
This is how prefix search works in the DB!

Precision Levels

1 char → huge area (continent)
2 chars → large area (country)
5 chars → ~4.9 km neighborhood ★
6 chars → ~1.2 km street ★
9 chars → ~4.8 m person

The Edge Problem

⚠️ Boundary Issue Cell 2 and cell 3 are neighbours, but their sub-cells (23 vs 30) have very different prefixes — even if they are centimetres apart. Always check 8 neighbours!

DB Search Pattern

1. Geohash user location (pick precision)
2. Get 8 neighbour cells
3. WHERE geohash IN (...9 cells...)
4. Filter by actual distance (Haversine)
5. Sort & return top N

🌲 Quadtree

Each node has 4 children: NW, NE, SW, SE. Cells split only when they get too crowded — the grid adapts to data density.

k = 5 (Threshold)

When a cell reaches 5 points, it splits into 4 quadrants and redistributes. Keep splitting until every cell has ≤ 5 points.

Adaptive Grid Dense area (city centre) → many small, deep cells
Sparse area (countryside) → one large shallow cell
Compare with geohash: the grid sizes are fixed regardless of data.

Tree Structure

○ = internal node (split into 4)
● = leaf node (holds actual points)

Leaf nodes are at different depths — dense areas are deeper in the tree.

Nearby Search

1. Walk tree → find leaf for query point
2. Return all points in that leaf
3. Not enough? → expand to parent/siblings
4. Filter by actual distance & return top N

🌐 Geohashing

✅
Works in any DB — simple prefix query (LIKE 'abc%')
✅
Stateless — just a string column, no special data structure
✅
Easy to shard: prefix → shard key
✅
Highly cacheable — same prefix = same data every time
✅
Great for static data (restaurants, POIs)
❌
Fixed grid — wastes cells in sparse areas
❌
Edge problem — close points can have completely different prefixes
❌
Cell shapes distort near the poles

🌲 Quadtree

✅
Adaptive — splits only where data is dense
✅
Cells are always rectangular, no distortion near poles
✅
Natural for range queries and spatial joins
✅
Ideal for real-time moving objects (Uber drivers)
❌
Needs in-memory tree or special DB (PostGIS, R-tree)
❌
Hard to shard across servers
❌
Must re-balance when data changes

📋 When to Use Which

ScenarioBest ChoiceReason
Yelp / Google Maps — nearby restaurantsGeohashStatic data, DB prefix query, easily cached
Tinder — nearby usersGeohashStore in user table, prefix search, cacheable
Uber / Lyft — nearby drivers (moving)QuadtreeReal-time updates, adapts to city density, in-memory
Game collision detectionQuadtreeIn-memory, fast, adapts to object clustering
Multi-server distributed systemGeohashPrefix → shard key, no cross-server coordination
Very uneven data distributionQuadtreeNo wasted cells in empty regions

📐 Distance Calculation

Haversine — accurate, works for large distances

a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlon/2)
c = 2·atan2(√a, √(1−a))
d = R·c  // R = 6,371 km

Simplified Euclidean — good enough for <100 km

Δlat_km = (lat2−lat1) × 111
Δlon_km = (lon2−lon1) × 111·cos(lat)
d = √(Δlat² + Δlon²)

Say "Haversine" in the interview, then use this simpler form to explain it.
